## 序言

IsoBase 源起一个朴素的想法：大多数自动化框架在你写下第一行代码之前，就已经替你选好了阵营——用什么工具、什么存储、什么 LLM 提供商。每一个选择都把你锁得更深，越往后越难变更。

IsoBase 反其道而行，先构建你的逻辑，再选择你的提供商，按照你的需要随时切换。

它是一个厂商中立的 Python 框架，围绕三根支柱构建：

- **JSON 驱动的工作流引擎** — 声明式定义执行树；工作单元将状态持久化到 SQLite，工作流可以暂停、恢复、在重启后继续运行。
- **厂商中立的 LLM 层** — 同样的 `ask()` / `generate()` / `generate_stream()` 调用，在 OpenAI Chat、Anthropic Messages、DashScope 或任何兼容端点上行为一致。多轮工具调用、流式输出、扩展思考、联网搜索均为内置能力。
- **可插拔的知识库 (RAG)** — 文档索引 → 向量嵌入 → 稠密 (cosine)、稀疏 (BM25) 或混合 (RRF 融合) 检索。三种存储后端（内存、SQL、Mongo），核心路径零额外依赖。

所有模块遵循同一原则：_默认简洁，高级功能按需开启_。

## 期望

我们相信自动化应该降低复杂度，而非增加它。IsoBase 为这样的实践者而设计：他们需要的框架是适应他们的技术栈——而不是反过来。

- **厂商中立** 意味着你的代码活得比你当前的供应商合同更长。
- **存储可移植**意味着你在内存上做原型、在 SQLite 上发布、在 PostgreSQL 或 MongoDB 上扩展——而无需重写任何检索逻辑。
- **最小依赖**意味着你不需要拉入一个向量数据库、一个中文分词器或一个你暂时用不到的云服务，就能安装并运行。

这是我们在每一个 Pull Request 中坚守的设计约束，如果你想要一个尊重你选择、而非替你选择的自动化框架，那就欢迎你使用并和我们一起持续改进 IsoBase。

## 项目进度

知识库模块的六个计划阶段已全部完成或已有规划：

| 阶段                                                | 状态         |
| --------------------------------------------------- | ------------ |
| 核心接口、分块、嵌入、内存存储                      | ✅           |
| SQL + Mongo 存储、生命周期 API、共享契约测试        | ✅           |
| Markdown 结构感知分块（`heading_path`、前置元数据） | ✅           |
| 检索增强（稠密 / 稀疏 / 混合 / RRF / 重排序）       | ✅           |
| 文档解析器                                          | 未来计划     |
| 向量索引后端（pgvector / FAISS）                    | 未来性能优化 |
